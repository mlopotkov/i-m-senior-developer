# Разработка через проверяемое поведение

## Purpose

Описать метод разработки, в котором проверка сначала обнаруживает отсутствие нужного поведения, затем подтверждает минимальное исправление и сохраняется при рефакторинге. Это требования к действиям модели по `tdd-master`, а не машинный запрет записи кода до теста.

## Requirements

### Requirement: Список сценариев предшествует реализации

Агент SHALL до реализации составлять список проверяемых сценариев, включая основной путь, значимые границы и ошибки, и последовательно проходить их через цикл RED–GREEN–REFACTOR.

#### Scenario: Добавляется новое исполняемое поведение
- **WHEN** задача требует нового поведения функции или команды
- **THEN** агент сначала перечисляет ожидаемые сценарии и выбирает первый отсутствующий результат для проверки

### Requirement: RED подтверждён наблюдаемым падением

Агент SHALL до запуска прогнозировать причину падения теста, запускать его и сравнивать фактическую причину с прогнозом; производственный код MUST не предшествовать тесту, падающему по нужной причине.

#### Scenario: Тест падает из-за неверной подготовки
- **WHEN** проверка падает при настройке фикстуры вместо проверки отсутствующего поведения
- **THEN** агент исправляет подготовку и повторяет проверку, не принимая этот запуск за доказанный RED нужного сценария

#### Scenario: Проверка всегда проходит
- **WHEN** тест проходит и при отсутствии проверяемого поведения
- **THEN** агент не принимает его как доказательство и уточняет проверку так, чтобы нарушение договора было обнаружимо

### Requirement: GREEN минимален, рефакторинг сохраняет результат

Агент SHALL писать только код, достаточный для выбранного падающего теста, выполнять рефакторинг после успешной проверки и сохранять проходящие тесты до перехода к следующему сценарию.

#### Scenario: Один сценарий стал проходить
- **WHEN** минимальная реализация удовлетворила текущую проверку
- **THEN** агент устраняет нужное дублирование или улучшает ясность в фазе REFACTOR, повторно проверяет результат и затем берёт следующий сценарий

### Requirement: Метод проверки учитывает проект и роль входа

Агент SHALL перед написанием тестов изучать зависимости, существующие тесты и конфигурацию, читать общие справки TDD и P0, а при обнаружении pytest или Django — соответствующие справки. Подготовка данных SHALL давать минимум для валидности зависимости, полноценный типичный вход для точки входа и явно обозначенные отклонения для граничных случаев.

#### Scenario: Проект использует pytest и Django
- **WHEN** зависимости и конфигурация подтверждают оба инструмента
- **THEN** агент читает обе профильные справки вместе с общими и использует принятый в проекте способ подготовки данных

#### Scenario: Проверяется точка входа
- **WHEN** тест должен доказывать типичный пользовательский путь
- **THEN** его вход по умолчанию полноценен для этого пути, а сокращённый или нетипичный вход задан явно как отдельный случай

### Requirement: Проверка сохраняет реальное поведение

Агент SHALL проверять одно наблюдаемое поведение на тест, не заменять собственную бизнес-логику моками и включать проверку бизнес-пути от входа до выхода. Один тест может проверять несколько результатов и побочных эффектов этого поведения. Для pytest параметризация MUST объединять разные данные одного поведения, а не переключать внутри теста разные действия и ожидания.

#### Scenario: Один путь принимает разные значения
- **WHEN** несколько наборов данных запускают один и тот же путь и отличаются только значениями
- **THEN** агент может объединить их параметризацией с общей проверкой результата

#### Scenario: Условия запускают разные действия
- **WHEN** один вариант должен создавать объект, а другой — только сообщать об ошибке
- **THEN** агент оформляет отдельные проверки поведения вместо ветвления проверки по параметру

### Requirement: Автоматический тест имеет наблюдаемый договор

В этом репозитории агент MUST обосновывать автоматический тест сохраняемым договором, запускающим входом, наблюдаемым результатом и ошибочной реализацией, которую тест обнаружит. Смысл документа или промпта SHALL проверяться ревью и поведенческими примерами; тест механизма доставки SHALL не подменять оценку содержания.

#### Scenario: Меняется только формулировка инструкции
- **WHEN** правка меняет смысл прозы без детерминированного машинного договора
- **THEN** агент до правки задаёт проверяемое ожидание и способ ревью или поведенческой оценки, не создавая тест поиска слов ради RED-фазы

#### Scenario: Меняется загрузка промпта
- **WHEN** код выбирает, собирает или передаёт промпт и результат можно наблюдать детерминированно
- **THEN** агент тестирует выбор, порядок, доставку и обработку отсутствующего входа как машинный договор
