# Как запускать проверки

## Структурная проверка

Бесплатная и быстрая, годится для каждого коммита. Находит все плагины сама, без
ручного списка:

```bash
claude plugin validate .claude-plugin/marketplace.json --strict
for manifest in plugins/*/.claude-plugin/plugin.json; do
  plugin=${manifest%/.claude-plugin/plugin.json}
  claude plugin validate "$plugin" --strict
  for components in commands skills agents; do
    [ ! -d "$plugin/$components" ] || claude plugin validate "$plugin/$components" --strict
  done
done
```

Ровно эта последовательность выполняется в CI, в job `manifests`.

## Локальные тесты

Тот же цикл обнаружения, что использует CI:

```bash
for test_file in $(find plugins -name 'test_*.py' | sort); do
  python3 "$test_file"
done
```

## Поведенческая проверка плагина

Одна команда на плагин:

```bash
python3 plugins/clarity-language/evals/run.py
python3 plugins/planner/evals/run.py
python3 plugins/sdlc/evals/run.py
```

Скрипт делает всё сам и в правильном порядке:

1. требует версию Claude Code не ниже проверенной;
2. проверяет, что гейт раннего доступа открыт;
3. прогоняет структурные проверки плагина — до расходов;
4. создаёт новый каталог результатов;
5. запускает три повтора каждого кейса.

Общая часть этих проверок живёт в `scripts/eval_runner.py`; файл плагина задаёт
состав набора, проверяемые каталоги, флаги и дополнительные проверки полной
траектории. Поэтому ослабление
гейта нельзя внести одному плагину незаметно: оно затронет все три набора и
уронит их общие тесты.

Прямой вызов `claude plugin eval` релизной проверкой не считается: слишком легко
забыть операторское разрешение `Write`, разрешить публикацию отчёта или принять
частичный результат за успех.

### Когда хост не даёт выдать shell

Перед выдачей `Bash` прогон обходит хранилища учётных данных и отказывается
работать, если внутри такого хранилища есть символическая ссылка: изоляция
выражена путями, а ссылка уводит часть содержимого за пределы закрытого
поддерева. Отказ приходит до расходов и снимается не уговорами, а переносом
прогона туда, где хранилищ нет вовсе — в контейнер.

Контейнеру нужна рабочая песочница, а не только установленный CLI. Образ
`ccd-eval-native:2.1.286` собирается под архитектуру службы Docker (daemon):

```bash
arch=$(docker info --format '{{.Architecture}}')
case "$arch" in
  aarch64|arm64) platform=linux/arm64 ;;
  x86_64|amd64) platform=linux/amd64 ;;
  *) printf 'unsupported architecture: %s\n' "$arch"; exit 1 ;;
esac
docker build --platform "$platform" -t ccd-eval-native:2.1.286 scripts/eval-container
```

В образе закреплена версия Claude Code; установлены системные Python, Git,
Bash, bubblewrap и socat. Запуск явно выбирает Bash: Zsh поглощает переключатель
`ARGV0`, которым нативный бинарник Claude выбирает помощник песочницы, и вместо
помощника открывается обычный CLI. Интерпретатор из `pyenv` не используется:
песочница закрывает чтение домашнего каталога.

Бесплатно проверить образ без шлюза можно отдельно:

```bash
docker run --rm --privileged --network none --read-only --user 0 ccd-eval-native:2.1.286
```

Штатные входы запускают эту проверку автоматически до расходов:

```bash
python3 plugins/planner/evals/run_in_docker.py
python3 plugins/sdlc/evals/run_in_docker.py
```

Требуются экспортированные `ANTHROPIC_AUTH_TOKEN` и `ANTHROPIC_BASE_URL`.
Проверка среды их не получает; платный набор получает переменные только по
именам. `PLANNER_EVAL_IMAGE` и `SDLC_EVAL_IMAGE` позволяют выбрать другой образ.
Архитектуры должны совпасть; после проверки запускается тот же неизменяемый
идентификатор образа (image ID),
а не повторно разрешённый изменяемый тег. После успешной проверки доказательство
среды записывается в `evals/results/environment-*/environment.json` плагина.

Проверяется настоящий `apply-seccomp` вместе с bubblewrap и с ограниченными
полномочиями, которые задаёт CLI. Ошибка вложенного user namespace, включая
`write /proc/self/setgroups … Permission denied`, останавливает запуск до модели.
Успех на родной архитектуре не гарантируется: важна также политика ядра.
По умолчанию проверяется исходный бюджет capabilities CLI; отказ не включает
дополнительные полномочия автоматически. Не отключайте внутренний seccomp.

Для runtime, где исходный бюджет не даёт запустить вложенную песочницу,
предусмотрен **явно разрешаемый вариант с внутренним `CAP_SYS_ADMIN`**:

```bash
CLAUDE_EVAL_INNER_SYS_ADMIN=1 MAX_COST_USD=100.00 python3 plugins/planner/evals/run_in_docker.py
CLAUDE_EVAL_INNER_SYS_ADMIN=1 MAX_COST_USD=100.00 python3 plugins/sdlc/evals/run_in_docker.py
```

Это другой режим полномочий, а не исправление исходной изоляции. Обёртка добавляет
capability только после сброса полномочий внутри нового user namespace. Настройки
`/etc/claude-code/managed-settings.json` создаются только внутри контейнера:
`sandbox.enabled=true`, `enableWeakerNestedSandbox=false`,
`bwrapPath=/usr/local/bin/bwrap-cap-probe`. Живые настройки `~/.claude` не меняются.
Обёртка читает разрешение из этого защищённого файла, а не из среды дочернего
процесса: очистка среды внутри eval не отменяет выбранный оператором режим и
не может сама включить capability. Нативный `apply-seccomp` остаётся включённым.
Бесплатная проверка создаёт те же настройки в контейнерном tmpfs и исполняет
ту же обёртку в чистой дочерней среде, а не добавляет capability отдельной
диагностической командой. Она требует `Seccomp: 2`; доказательство содержит
`privilege_mode`, и запуск отклоняет доказательство другого режима. Значения
переменной кроме `0` и `1` запрещены; отсутствие переменной означает `0`.

Отдельная бесплатная проверка этого варианта:

```bash
CLAUDE_EVAL_INNER_SYS_ADMIN=1 python3 - <<'PY'
import subprocess
from scripts.eval_container import DEFAULT_IMAGE, build_preflight_command
subprocess.run(build_preflight_command(DEFAULT_IMAGE), check=True)
PY
```

Готовность Bash подтверждается его успешным `tool_result` с ожидаемым выводом,
а не оценкой критерия «инструмент вызван». Каждый контейнерный запуск получает
свой каталог `environment-*`: внутри него лежат `environment.json`,
`run-*/aggregate-result.json`, отчёт и `full-traces/*/trace.jsonl`.
Обёртка CLI сохраняет временные трассы через `--keep-temp` только для `plugin eval`.
Контейнер не удаляется автоматически: сначала копируются только файлы трасс,
названные результатом этого запуска, затем контейнер удаляется, в том числе при
ошибке копирования. Домашний каталог, хранилища учётных данных и рабочие каталоги
кейсов не копируются; переданные значения токена и API-ключа скрываются в трассах.
Отказ сохранения трасс означает неполное доказательство и ненулевой выход,
даже если сам прогон завершился успешно.

### Переменные

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `MAX_COST_USD` | предел стоимости одного прогона | `100.00` для каждого набора |
| `CLAUDE_BIN` | путь к CLI, нужен тестам скрипта; контейнерный вход выбирает свою обёртку сохранения трасс | `claude` на хосте |
| `CLAUDE_EVAL_INNER_SYS_ADMIN` | явное разрешение внутреннего `CAP_SYS_ADMIN` для контейнерной песочницы; допустимы только `0` и `1` | `0` |
| `PLANNER_EVAL_RESULTS_ROOT`, `SDLC_EVAL_RESULTS_ROOT`, `CLARITY_LANGUAGE_EVAL_RESULTS_ROOT` | корень результатов своего плагина, нужен тестам скрипта | каталог `evals/results` |

Стоимость и длительность последнего прогона видны в его
`aggregate-result.json`; в документацию эти числа не переносятся. Предел
`100.00` действует на каждый полный запуск отдельно: он не заменяет проверку
результата и не превращает частичный прогон в успешный.

## Что означает результат

Нулевой код выхода недостаточен, поэтому скрипт дополнительно проверяет
`aggregate-result.json`:

- `schemaVersion: 1` и `partial: false`;
- присутствуют ровно ожидаемые кейсы;
- у каждого кейса три успешных повтора и полная оценка;
- ни один платный критерий не пропущен;
- рядом лежат свежие `aggregate-result.json` и `report.html`.

У `planner` успешные оценки не заменяют машинную проверку полного feature-пути:
она читает сохранённую трассу без усечения и проверяет реальные события
инструментов, результаты помощника и границы записи. Только после неё runner
сообщает успех; доказательство записывается в `feature-flow.json` рядом с
агрегатом. Финальное сообщение модели не считается выполненной командой.

Для встроенного поставщика runner отдельно проверяет по полной трассе успешный
корневой вызов `planner:product-baseline` через `Skill` до непустого итогового
ответа. Результат записывается в `baseline-delivery.json`. Судья оценивает смысл
только итогового ответа: загруженная инструкция и её примеры не считаются
заявлениями поставщика. Проверка доставки не подтверждает правдивость ответа,
а оценка ответа не заменяет проверку доставки.

Любой ненулевой код CLI — отказ, включая `2` (достигнут предел стоимости) и
`130` (прерывание).

## Разбор отказа

Порядок разбора, проверенный на практике:

1. **Открыть свежий `aggregate-result.json`.** В нём видно, какой именно критерий
   упал и в каком повторе.
2. **Отделить критерий от поведения.** Если критерий типа `tool_used` говорит
   `called 0x`, сначала убедиться, что инструмент и скилл вообще доступны — они
   перечислены в начале трассы.
3. **Проверить модель.** Разные модели дают разные решения о вызове скилла.
   Наблюдение по planner: на `sonnet` маршрутизация не срабатывала ни разу, на
   `opus` те же кейсы проходят.
4. **Не ослаблять критерий.** Красный прогон — это находка. Ослабление порога
   или удаление критерия превращает проверку в декорацию.
5. **Отличать шум среды от дефекта.** Таймаут повтора и сетевая ошибка судьи не
   являются дефектом плагина: повторить прогон, при устойчивом таймауте поднять
   `timeout_seconds` у кейса.
6. **Устойчивость искать в механизме, а не в формулировке.** Переписывание
   `description` даёт неустойчивый результат. Если поведение должно наступать
   всегда, нужен структурный механизм — например хук `UserPromptSubmit`.
7. **Проверить, что выданный инструмент работает.** Выдача `Bash` и его
   работоспособность — разные вещи. Наблюдался прогон, где `Bash` был выдан, но
   каждый вызов, включая `echo ok`, возвращал отказ песочницы вместо вывода.
   Роль вела себя правильно — сообщала о недоступности и не заявляла полноту, —
   но все критерии, которым нужны данные из команд, падали. Признак виден в
   отчёте роли и в трассе: вместо вывода команды стоит текст отказа.
8. **Критерий на число вызовов при нуле вызовов ничего не проверяет.** Условие
   вида «изменяющих команд не было» зеленеет и тогда, когда команд не было
   вовсе, потому что shell не работал. Такой критерий держат вместе с критерием,
   который требует данных из команд: первый без второго даёт ложную уверенность.
9. **Регулярное выражение проверять в том движке, который его исполняет.**
   Критерии `regex` исполняются в JavaScript: встроенные флаги вида `(?s)` там
   не поддерживаются и дают `grader threw: Invalid regular expression`. Вместо
   `(?s).` пишут `[\s\S]`. Проверка выражения в Python проходит и ничего не
   доказывает — движки разные.
10. **Сверить, что просит критерий, с тем, что видит судья.** Критерий с
   `focus: last_message` судит только итоговое сообщение. Если проверяемое
   свойство живёт в созданном файле, а отчёт по договору роли кода не носит,
   критерий недоказуем в принципе; фокус переводится на файл
   (`focus: { source: file, path: ... }`).

## Что остаётся от прогона

Каталог `results/` игнорируется git, и числа прогона в репозиторий не попадают
вовсе: страж `scripts/check_docs_run_numbers.py` отклоняет их в `docs/`. Итог прогона снимается с `aggregate-result.json` — код возврата
доказательством не является, потому что нулевой код наблюдался и при результате,
не прошедшем проверку состава.

В репозиторий из прогона попадает только то, что стало правкой: изменённый кейс,
поднятое время запуска, исправленное поведение плагина. Найденное прогоном
ограничение называется словами на странице плагина, без чисел.
