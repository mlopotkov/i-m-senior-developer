# Как запускать проверки

## Структурная проверка

Бесплатная и быстрая, годится для каждого коммита. Находит все плагины сама, без
ручного списка:

```bash
claude plugin validate .claude-plugin/marketplace.json --strict
for manifest in plugins/*/.claude-plugin/plugin.json; do
  plugin=${manifest%/.claude-plugin/plugin.json}
  claude plugin validate "$plugin" --strict
  for components in commands skills agents; do
    [ ! -d "$plugin/$components" ] || claude plugin validate "$plugin/$components" --strict
  done
done
```

Ровно эта последовательность выполняется в CI, в job `manifests`.

## Локальные тесты

Тот же цикл обнаружения, что использует CI:

```bash
for test_file in $(find plugins -name 'test_*.py' | sort); do
  python3 "$test_file"
done
```

## Поведенческая проверка плагина

Одна команда на плагин:

```bash
python3 plugins/planner/evals/run.py
python3 plugins/sdlc/evals/run.py
```

Скрипт делает всё сам и в правильном порядке:

1. требует версию Claude Code не ниже проверенной;
2. проверяет, что гейт раннего доступа открыт;
3. прогоняет структурные проверки плагина — до расходов;
4. создаёт новый каталог результатов;
5. запускает три повтора каждого кейса.

Общая часть этих проверок живёт в `scripts/eval_runner.py`; файл плагина задаёт
только состав набора, проверяемые каталоги и флаги прогона. Поэтому ослабление
гейта нельзя внести одному плагину незаметно: оно затронет все три набора и
уронит их общие тесты.

Прямой вызов `claude plugin eval` релизной проверкой не считается: слишком легко
забыть операторское разрешение `Write`, разрешить публикацию отчёта или принять
частичный результат за успех.

### Когда хост не даёт выдать shell

Перед выдачей `Bash` прогон обходит хранилища учётных данных и отказывается
работать, если внутри такого хранилища есть символическая ссылка: изоляция
выражена путями, а ссылка уводит часть содержимого за пределы закрытого
поддерева. Отказ приходит до расходов и снимается не уговорами, а переносом
прогона туда, где хранилищ нет вовсе — в контейнер.

Контейнер ставит собственное условие: Claude Code не выдаёт shell без рабочей
песочницы, а её зависимости `bubblewrap` и `socat` в образ обычно не входят.
Дальше многое зависит от ядра. На виртуальной машине Colima наблюдалась такая
картина: без привилегий контейнера bubblewrap не создаёт пространство имён
вовсе, `sandbox.enableWeakerNestedSandbox` этого не меняет, а под привилегиями
падает уже внутренний seccomp-слой — `prctl(PR_SET_SECCOMP): Invalid argument`.
Рабочая форма оставляет внешней границей контейнер, сохраняет файловую и сетевую
изоляцию bubblewrap и снимает только внутренний seccomp-слой через
`sandbox.bwrapPath`, указывающий на обёртку.

Кейсу нужен и его собственный инструмент: песочница закрывает чтение домашнего
каталога, поэтому интерпретатор из `pyenv` кейсу недоступен и python ставится в
системные пути образа. Признак этой беды в отчёте роли — честное «тесты не
запускались» рядом с названной заблокированной командой.

### Переменные

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `MAX_COST_USD` | предел стоимости прогона | `6.00`, у `sdlc` — `38.00` |
| `CLAUDE_BIN` | путь к CLI, нужен тестам скрипта | `claude` |
| `PLANNER_EVAL_RESULTS_ROOT`, `SDLC_EVAL_RESULTS_ROOT`, `CLARITY_LANGUAGE_EVAL_RESULTS_ROOT` | корень результатов своего плагина, нужен тестам скрипта | каталог `evals/results` |

Стоимость и длительность последнего прогона видны в его
`aggregate-result.json`; в документацию эти числа не переносятся. Предел `6.00`
оставляет запас над измеренной стоимостью, не давая прогону уйти в
неограниченный расход.

## Что означает результат

Нулевой код выхода недостаточен, поэтому скрипт дополнительно проверяет
`aggregate-result.json`:

- `schemaVersion: 1` и `partial: false`;
- присутствуют ровно ожидаемые кейсы;
- у каждого кейса три успешных повтора и полная оценка;
- ни один платный критерий не пропущен;
- рядом лежат свежие `aggregate-result.json` и `report.html`.

Любой ненулевой код CLI — отказ, включая `2` (достигнут предел стоимости) и
`130` (прерывание).

## Разбор отказа

Порядок разбора, проверенный на практике:

1. **Открыть свежий `aggregate-result.json`.** В нём видно, какой именно критерий
   упал и в каком повторе.
2. **Отделить критерий от поведения.** Если критерий типа `tool_used` говорит
   `called 0x`, сначала убедиться, что инструмент и скилл вообще доступны — они
   перечислены в начале трассы.
3. **Проверить модель.** Разные модели дают разные решения о вызове скилла.
   Наблюдение по planner: на `sonnet` маршрутизация не срабатывала ни разу, на
   `opus` те же кейсы проходят.
4. **Не ослаблять критерий.** Красный прогон — это находка. Ослабление порога
   или удаление критерия превращает проверку в декорацию.
5. **Отличать шум среды от дефекта.** Таймаут повтора и сетевая ошибка судьи не
   являются дефектом плагина: повторить прогон, при устойчивом таймауте поднять
   `timeout_seconds` у кейса.
6. **Устойчивость искать в механизме, а не в формулировке.** Переписывание
   `description` даёт неустойчивый результат. Если поведение должно наступать
   всегда, нужен структурный механизм — например хук `UserPromptSubmit`.
7. **Проверить, что выданный инструмент работает.** Выдача `Bash` и его
   работоспособность — разные вещи. Наблюдался прогон, где `Bash` был выдан, но
   каждый вызов, включая `echo ok`, возвращал отказ песочницы вместо вывода.
   Роль вела себя правильно — сообщала о недоступности и не заявляла полноту, —
   но все критерии, которым нужны данные из команд, падали. Признак виден в
   отчёте роли и в трассе: вместо вывода команды стоит текст отказа.
8. **Критерий на число вызовов при нуле вызовов ничего не проверяет.** Условие
   вида «изменяющих команд не было» зеленеет и тогда, когда команд не было
   вовсе, потому что shell не работал. Такой критерий держат вместе с критерием,
   который требует данных из команд: первый без второго даёт ложную уверенность.
9. **Регулярное выражение проверять в том движке, который его исполняет.**
   Критерии `regex` исполняются в JavaScript: встроенные флаги вида `(?s)` там
   не поддерживаются и дают `grader threw: Invalid regular expression`. Вместо
   `(?s).` пишут `[\s\S]`. Проверка выражения в Python проходит и ничего не
   доказывает — движки разные.
10. **Сверить, что просит критерий, с тем, что видит судья.** Критерий с
   `focus: last_message` судит только итоговое сообщение. Если проверяемое
   свойство живёт в созданном файле, а отчёт по договору роли кода не носит,
   критерий недоказуем в принципе; фокус переводится на файл
   (`focus: { source: file, path: ... }`).

## Что остаётся от прогона

Каталог `results/` игнорируется git, и числа прогона в репозиторий не попадают
вовсе: страж `scripts/check_docs_run_numbers.py` отклоняет их в `docs/`. Итог прогона снимается с `aggregate-result.json` — код возврата
доказательством не является, потому что нулевой код наблюдался и при результате,
не прошедшем проверку состава.

В репозиторий из прогона попадает только то, что стало правкой: изменённый кейс,
поднятое время запуска, исправленное поведение плагина. Найденное прогоном
ограничение называется словами на странице плагина, без чисел.
