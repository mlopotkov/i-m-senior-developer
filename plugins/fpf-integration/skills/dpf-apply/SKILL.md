# dpf-apply — резолвер и исполнитель пакетов компетенций

Скилл сам не содержит ни одной компетенции. Он резолвит id пакета (`DPF-…` / `LPF-…`) до файла на диске и запускает нужный режим использования — как знание (ground) или как процедуру с типизированным выходом (apply). Каждое использование — пара «пакет × объявленное применение» (E.4.DPF.DA: `declaredUse`, `nonUseBoundary`, `intendedReaderOrOperator`, `reopenCondition`); скилл не даёт применить пакет «просто так», без этой пары.

`packageKind` включает `local-practice-framework` и `skill-pack` — сам `dpf-apply` при установке из плагина является пакетом `kind=skill-pack` (см. README, сценарий 3).

## Резолюция

```bash
python3 <каталог этого скилла>/scripts/resolve.py <id> [--json]
python3 <каталог этого скилла>/scripts/resolve.py --list [--json]
python3 <каталог этого скилла>/scripts/resolve.py --sources [--json]
```

Каталог скилла — тот, из которого прочитан этот файл; при установке из плагина это `plugins/fpf-integration/skills/dpf-apply`.

Порядок уровней (первый выигрывает при затенении id):

1. **project** — `$PWD/.claude/.dpf/<ID>/`, затем корни построчно из `$PWD/.claude/.dpf.paths` (относительная строка читается от корня проекта)
2. **user** — `~/.claude/.dpf/<ID>/`
3. **plugin** — непустые строки без комментариев из `~/.claude/.dpf.paths`, затем каталог ссылок банков `~/.claude/dpf.d/`

Прежние имена того же назначения читаются **следом за каноническими внутри своего уровня**: `.claude/frameworks` и `.claude/frameworks.paths` у проекта, `~/.claude/frameworks` у пользователя, `~/.claude/frameworks.paths`, `~/.claude/frameworks.d` и `~/.claude/frameworks.published` на уровне подключённых источников. Перенос на канонические имена выполняет отдельная команда — он не происходит сам:

```bash
python3 <каталог этого скилла>/scripts/migrate_dpf_paths.py            # только показать план
python3 <каталог этого скилла>/scripts/migrate_dpf_paths.py --apply    # выполнить
```

Если новая публикация уже принадлежит тому же банку и обе ссылки исправны, команда сохраняет её и убирает проверенные прежние ссылки; чужая или неполная публикация блокирует весь план. Обнаруженный до записи конфликт (занятое имя каталога, чужая ссылка, отсутствующая запись владельца) даёт код `3` без изменений. Ошибка ввода-вывода во время `--apply` даёт код `4`: часть операций могла выполниться, отката нет — повторно проверь пути перед новым запуском. Файл `frameworks.published` команда не переносит: его строки принадлежат банкам.

Повторные корни исключаются по каноническому пути; остаётся первое вхождение. Файлы `.dpf.paths` — человеческие списки: резолвер читает их, но не записывает. `--sources` печатает по строке на каждый объявленный корень: уровень, происхождение (`project`, `project-paths`, `project-legacy`, `project-paths-legacy`, `user`, `user-legacy`, `paths`, `banks`, `paths-legacy`, `banks-legacy`, `published`), путь и существование каталога; режим всегда завершается кодом `0`.

В каталог `~/.claude/dpf.d/` каждый банк кладёт по ссылке на свой свод и владеет только своими записями, поэтому два банка сосуществуют. Служебный подкаталог `.fpf_banks/<имя банка>/` сводом не считается.

Пригодность свода не зависит от того, каким путём он найден. Отказ кодом `2` дают: нарушенная форма (нет обязательного поля, `kind` вне набора, `dpf_id` не совпадает с именем каталога), просроченный или неактивный свод, отрицательная либо нечитаемая оценка `E.4.DPF.DA` и её отсутствие. Проект может назвать своды в `.claude/.dpf.trusted` по одному идентификатору в строке — это снимает **только отсутствие оценки** и только в этом проекте. Отрицательную оценку, просрочку и сломанную форму доверие не отменяет, положительным заключением оценщика не является и решение ответственного человека о допуске для заявленного применения не заменяет. Поля `assessment`, `trusted_by_project`, `admissible` и `structure_problem` в выдаче `--json` показывают состояние машинно; `--list` помечает строку как «без допуска» или «по доверию проекта», подсказка недопущенный свод не предлагает.

Полный id вида `plugin:<ID>` минует уровни project/user и ищет среди всех plugin-путей — используй, когда явно нужен пакет из конкретного плагина, а не локальная переопределяющая копия.

Пакет = каталог `<root>/<ID>/` с файлом `DPF.md` (YAML-frontmatter: `dpf_id`, `kind`, `status`, `review_due`, `owner`, …). Исполнимость пакета = наличие `assets/apply-prompt.md` рядом с `DPF.md`.

## Гейт свежести (всегда перед использованием)

`resolve.py` возвращает exit-код:

- `0` — пакет найден и пригоден (форма цела, `status == active`, `review_due` не истёк, оценка положительная либо свод назван в проектном списке доверия) → работать дальше.
- `1` — пакет не найден ни на одном уровне → **отказ**, id не существует, работа невозможна.
- `2` — пакет найден, но применять нельзя: протух (`status != active`, ИЛИ `review_due` истёк/отсутствует/не парсится), нарушена форма или нет положительной оценки → **отказ с эскалацией владельцу** (поле `owner` из вывода). Причину резолвер называет в сообщении. Работа по протухшему своду запрещена — свод либо устарел содержательно, либо просрочен плановый пересмотр (E.4.DPF.DA), в обоих случаях решение не мейнтейнера скилла, а владельца пакета.

Отдельно проверь **edition-пин**, если вызывающий агент/скилл несёт зависимость с явной редакцией (`targetRef@edition` в его relation-record, см. README сценарий 2/3): если `fpf_edition` пакета разошёлся с запиской потребителя — то же самое, отказ с эскалацией, а не молчаливая работа по чужой редакции.

## Три режима

### `--list` — слитая карта компетенций

Показывает все пакеты по всем уровням, затенённые id помечены `[shadowed]`, протухшие — `[stale]`. Используй, когда пользователь спрашивает «какие компетенции есть» / нужно выбрать id вслепую.

### Ground — пакет без apply-ассетов

Если `executable: нет` (нет `assets/apply-prompt.md`) — применение-как-знание: прочитать `DPF.md` целиком в контекст текущей задачи (`Read <path>/DPF.md`) и работать по нему напрямую — самому пройти его паттерны/чек-листы применительно к задаче. Отдельного агента не спаунить, выходной схемы нет.

### Apply — пакет с `assets/apply-prompt.md`

Исполняемый пакет — процедура с типизированным выходом:

1. Прочитать `<path>/assets/apply-prompt.md` (промпт роли) и `<path>/assets/finding-schema.json`, если есть (контракт выхода).
2. Спаунить агента: вход = `apply-prompt.md` + конкретный вход задачи (дифф, кандидат, вопрос). Выход агента обязан строго соответствовать `finding-schema.json` — не текстом произвольной формы.
3. Механические проверки оркестратора после ответа агента (сам dpf-apply, не агент):
   - число вердиктов в ответе == числу кандидатов, поданных на вход (пропуски запрещены — молчание не значит «нет находки»);
   - находки с `route=maintainer` не принимаются автоматически — только эскалация, решение не за исполнителем;
   - каждая находка типа Boundary от LLM-исполнителя обязана нести `pending_human_confirmation: true` — граничные случаи пакета сам агент не закрывает;
   - эскалация сканируется по ВСЕМУ `candidates[]`, не только по top-level `findings[]`: кандидат с `route=maintainer` + `pending_human_confirmation` подлежит эскалации при ЛЮБОМ `decision` (в т.ч. `keep`/`defer`) — top-level список может индексировать лишь часть решений (например, только `generalize`), и находка иного рода (гейт ширины контракта и т.п.) не должна стать терминологически невидимой.

## Журнал применений (worked-evidence)

После каждого РЕАЛЬНОГО применения — ground (свод прочитан и применён к задаче) или apply (агент отработал по apply-промпту), но не `--list` и не отказ гейта свежести — допиши одну строку в журнал целевого пакета: `<путь пакета>/references/worked-evidence.md` (рядом с его `DPF.md`; файла нет — создай). Это данные момента применения: сейчас ты единственный, кто знает всё для записи.

Формат строки (един для всех писателей журнала, не переформулировать):

```
- YYYY-MM-DD · <якорь: сессия | MR/коммит/файл> · ground|apply|direct · Паттерн N «имя» · что произошло (1-2 фразы) · исход: подтверждает / опровергает / показал границу / TBD
```

- **Якорь** — что конкретнее привязывает событие: MR/коммит, файл или сессия.
- **Редакция пакета** — добавь в поле «что произошло», если у пакета есть `fpf_edition` или дата редакции: сверка при пересмотре пакета должна знать, по какой редакции работали.
- **Исход `TBD`** — норма, если в момент применения он не ясен: его закроет шаг worked-evidence ритуала end-session.

Если в проекте нет `.claude/commands/end-session.md` — добавь в конец отчёта применения одну строку (и больше ничего: никаких файлов проекта этот скилл не создаёт и не правит):

> Журнал применений веду, но исходы некому закрывать — в проекте нет ритуала end-session. Поставь: `/fpf-integration:end-session-setup`.

## Дисциплина (не нарушать)

- **Пакет не копируется в промпты.** Carrier (файл `DPF.md` в конкретном каталоге) ≠ framework edition (содержательная версия свода). Промпту передаётся ссылка на путь + прочитанное содержимое по требованию, не встроенная копия «на будущее» — иначе копия расходится с оригиналом при следующем пересмотре пакета и никто об этом не узнает.
- **Ссылки потребителей — только по id с edition-пином**, в форме типизированной записи E.4.PFR (`sourceRef` / `targetRef@edition` / `relationFunction` / `governedUse` / `directGoverningPatternRef` / `dependencyOrEditionEffect`), не «просто ссылкой». Пример — README, сценарий 2.
- **Зависимость однонаправленная** (E.5.3): потребитель → свод. Свод никогда не знает и не ссылается на своих потребителей (CC-DPFDA.6b).
- **Вход в использование — PUR-форма** (E.11 / E.11.PUR, `PatternUseRecommendation@Context`): концерн → кандидатные применения → рекомендованное применение → ожидаемый первый результат. Отдельный first-entry индекс поверх этого не ведётся, если он дублирует сценарии README (CC-E11-3) — сценарии README и есть точка входа.
