# Кейсы проверки ролей sdlc

## Что покрыто

| Кейс | Что проверяет |
|---|---|
| `working-tree-coverage` | ревью текущего рабочего дерева относительно base: охват staged, unstaged, совмещённого файла, untracked внутри области, удаления и обеих сторон переименования; отдельным критерием — исключение файлов вне области и игнорируемого внутри области, плюс разбор совмещённого файла по конечному содержимому; поле полноты охвата |
| `commit-range-coverage` | ревью диапазона коммитов разбирает только закоммиченное и не захватывает локальные правки и неотслеживаемые файлы |
| `invalid-base-stop` | неразрешимый base останавливает ревью и не подменяется другой точкой отсчёта |
| `empty-target-coverage` | область без изменений называется пустой, а не чистым ревью |
| `mined-guards-code-diff` | ревью кодового диффа: повторно выведенный признак против названного владельца, совместимость схемы вместо точного равенства, тест мимо событийного механизма, англицизм в значении перевода без ложного срабатывания на названии марки, второй дефект отдельной находкой, отсутствие выдуманного профильного прохода |
| `mined-guards-prose-diff` | дифф без исполняемого кода: обход списка уязвимостей пропущен, раздел безопасности и поиск ключей остались, переопределённый термин пойман чтением файла целиком, предложение сверено с уже принятым решением |
| `mined-guards-architect` | стек без справочника: единица границы взята из самого стека, каждый критерий приёмки прослежен до контекста, выпущен проверяемый запрет импорта |
| `mined-guards-implementer` | разбор вложенных данных со счётом скобок и учётом кавычек, тесты на вложенность и на скобку в строке, раздел рисков отдельно от допущений |
| `orchestrated-report-write` | роль, вызванная субагентом с зарезервированным пустым путём, заполняет файл полным отчётом по своему шаблону и не отвечает отказом писать отчётный файл |

Каждый кейс готовит свой временный репозиторий скриптом `fixture.sh` и
запускается только с явным `--scaffold`.

## Запуск

Полный релизный прогон из корня репозитория в среде, где Bash работает без
дополнительной изоляции:

```bash
python3 plugins/sdlc/evals/run.py
```

Для контейнерного прогона сначала экспортируйте переменные шлюза в текущую
оболочку, затем используйте штатный запуск:

```bash
python3 plugins/sdlc/evals/run_in_docker.py
```

Контейнер получает значения переменных по именам: токен не входит в аргументы
команды. Запуск задаёт системный `PATH` без каталогов `pyenv`, использует
`/usr/bin/python3` и перед стартом открывает только проход через `/home/agent`,
чтобы внутренняя песочница могла подключить системные каталоги. Файлы домашнего
каталога от этого не становятся читаемыми. Образ можно заменить переменной
`SDLC_EVAL_IMAGE`; по умолчанию используется `ccd-eval-py:latest`.

Обёртка до расходов проверяет версию Claude Code, доступность `plugin eval` и
структуру плагина строгой валидацией, затем запускает три повтора каждого кейса
параллельно (`--concurrency 2`) и отклоняет частичный результат, пропущенный кейс, неполные повторы и пропуск
платного критерия. Предел расходов задаётся переменной `MAX_COST_USD`, по
умолчанию `38.00` — девять кейсов на модели opus по три повтора каждого, по наблюдённой цене повтора с запасом. Доля `orchestrated-report-write` выше прочих: его повтор оплачивает и оркестратора, и вызванного им субагента. Два повтора идут параллельно, третий следом: три одновременные сессии наблюдённо выбивают общий лимит учётной записи, а две сохраняют часть выигрыша по времени. Заниженный предел не экономит: прогон обрывается на середине, а истраченное до обрыва пропадает вместе с частичным результатом. Общая часть гейта живёт в `scripts/eval_runner.py` и одинакова
для всех плагинов; здесь задан только состав набора и флаги прогона.

Отладка одного кейса прямым вызовом CLI релизной проверкой не считается:

```bash
claude plugin eval . \
  --eval-dir plugins/sdlc/evals \
  --case working-tree-coverage \
  --ablation none \
  --runs 1 \
  --scaffold \
  --allow-tools Bash \
  --no-publish
```

Результаты остаются в `plugins/sdlc/evals/results/` и в документацию не
переносятся.

## Один кейс — много критериев

Стоимость прогона растёт от числа кейсов, а не от числа проверяемых правил:
каждый кейс готовит свою заготовку и повторяется трижды. Поэтому правила
сгруппированы по виду входа, а внутри кейса каждое правило получает свой файл
критерия. Добавляя правило, ищите кейс с подходящим входом прежде, чем заводить
новый кейс.

Критерий называет и условие прохода, и условие провала, а в заготовке рядом с
нарушением лежит безобидный сосед, который отмечаться не должен: критерий,
проверяющий только срабатывание, зеленеет и на роли, которая отмечает всё
подряд.

Один критерий — один вопрос. Наблюдение по `working-tree-coverage`: критерий,
соединявший десять условий об охвате, давал расхождение судей на длинном отчёте,
и каждый повтор ронял его по-своему, хотя отчёты были верны по существу.
Перечисление путей вынесено в машинный `regex`, остальное разведено по вопросам:
удаление, переименование, исключения. Судья отвечает на короткий вопрос
устойчивее, чем сверяет длинную конъюнкцию.

Выражение критерия `regex` исполняется в JavaScript: встроенные флаги вида
`(?s)` там не поддерживаются, вместо `(?s).` пишут `[\s\S]`. Проверка
выражения в Python проходит и ничего не доказывает.

## Границы кейсов

Кейсы наблюдают вызовы инструментов и итоговый отчёт. Запрет изменяющих команд
проверяется по фактическим вызовам `Bash`, а не по тексту отчёта: упоминание
`git add` внутри находки — это диагноз, а не действие. Состояние файловой
системы после прогона кейсы сами не сверяют, поэтому в обычном прогоне
неизменность рабочего дерева держится на отсутствии изменяющих вызовов.

`orchestrated-report-write` — единственный кейс, где роль вызывается агентом, а
не активируется скиллом в той же сессии. Так сделано намеренно: проверяемое
давление живёт в системном промпте субагента и в главной сессии не
воспроизводится. Инструмент `Agent` оператор не гейтит, кейсу достаточно назвать
его в своём `allowed_tools`.

Граница этого кейса: он не доказывает, что файл записала именно роль, а не
оркестратор. Доказательства косвенные и держатся вдвоём — вызов субагента виден
в трассе, а в файле стоит строка шаблона роли `References loaded:`, которой в
задании кейса нет.

Отдельно неизменность рабочего дерева доказывается прогоном с сохранением
песочницы:

```bash
# эталон: та же подготовка в пустом каталоге
mkdir /tmp/fixture && cd /tmp/fixture
bash <репозиторий>/plugins/sdlc/evals/working-tree-coverage/fixture.sh
python3 <репозиторий>/scripts/worktree_fingerprint.py /tmp/fixture > /tmp/expected.json

# сверка сохранённой песочницы прогона
python3 scripts/worktree_fingerprint.py <сохранённая песочница>/home/cwd /tmp/expected.json
```

Отпечаток собран из содержимого и структуры, а не из времени: имя ветки,
отношение HEAD к меткам, состояние индекса, состав неотслеживаемых файлов и
хеши содержимого. Правка файла и добавление в индекс отличаются от эталона.

## Почему прогон нацелен на корень репозитория

Плагин, у которого объявлена зависимость, загружается только вместе с ней: без
неё хост понижает его целиком, скиллы ролей исчезают, и на вызов
`sdlc:code-reviewer` приходит `Unknown skill`. В следе такого прогона это видно
прямо: `"plugins": []` и `plugin_errors` с записью `dependency-unsatisfied`.

Кейс вправе называть в поле `plugins` только то, что лежит под containment root,
а им становится каталог, на который нацелен запуск. Поэтому прогон нацелен на
корень репозитория, а каталог кейсов назван флагом `--eval-dir
plugins/sdlc/evals`: тогда под корнем оказываются и `sdlc`, и `tdd-master`, и
`functional-clarity`, и каждый кейс называет все три. Проверено следом: в шапке
прогона три плагина, `plugin_errors` пуст, `sdlc:architect` есть в списке
скиллов.

Задание кейса всё равно разрешает прочитать файл скилла, если инструмент его не
выдаёт: это запасной путь, а не основной.

Критерий `tool_used` на скилле из набора убран: он считает вызов, а не успешную
загрузку, и поэтому зачитывает неудачный вызов как успех. Наблюдались повторы,
где два кейса показали полный счёт, хотя договор роли не применялся вовсе.

Применение договора различает строка из шаблона роли, которой в задании кейса
нет: у ревьюера и архитектора это `References loaded:`, у реализатора — заголовок
`Verification beyond the suite`. Критерий на неё стоит в каждом кейсе, где
печатается отчёт или документ, и отделяет проверенный договор от работы по одному
заданию. Без него кейс зеленеет на общей практике: наблюдался прогон
архитектурного кейса, где плагин не загрузился вовсе, а два критерия из трёх всё
равно прошли.

В `invalid-base-stop` отчёт по договору не печатается вовсе: роль обязана
остановиться на неразрешимом base до сбора изменений. Там признаком служит
ссылка на справочник договора или шапка отчёта — что из двух появится, зависит
от того, насколько далеко роль успела пройти до остановки.
